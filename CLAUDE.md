# Reformulation Assistant — правила проєкту для Claude Code

Pet-проєкт під вакансію Backend & AI Engineer у харчовій R&D. Мета: за ~8 годин зібрати
робочий сервіс, який демонструє весь стек із вакансії (FastAPI, Postgres+pgvector, Docker,
LLM, RAG, агент з інструментами) і придатний для демо на співбесіді.

Головне правило роботи: Claude пише код, людина тримає архітектуру і перевіряє кожен блок
руками (курл, а не "повірити на слово"). На співбесіді запитають "чому так", а не "хто писав".

## Що будуємо

HTTP-сервіс: технолог подає рецептуру продукту і ціль зміни (прибрати алерген / зменшити
цукор / зробити веганським), сервіс повертає обґрунтовану пропозицію замін інгредієнтів із
джерелами і порівнянням нутрієнтів до/після. Три частини: база знань (Postgres+pgvector),
RAG-пошук (/ask), агент переформулювання (/reformulate) з tool calling.

Фронтенду немає — демо через Swagger UI (`/docs`).

## Жорсткі правила (не порушувати)

- **Без фреймворків для агента.** Ніякого LangChain/LlamaIndex — свій цикл tool calling на
  ~50 рядків. За день фреймворк з'їсть більше часу на дебаг, ніж зекономить.
- **Один клас `LLMClient`**, два методи: `complete` і `complete_with_tools`. Провайдер
  обирається лише через змінну оточення `LLM_PROVIDER` (`gemini` / `groq`). Перемикання між
  провайдерами — заміна однієї змінної, без переписування коду.
- **Тести ніколи не викликають живий LLM.** Тільки `app/llm/fake.py` (`FakeLLM`), який
  повертає задані відповіді. Живий LLM спалює безкоштовний ліміт і падає випадково.
- **Формат помилок єдиний:** `{"error": {"code": "...", "message": "..."}}`. Помилки агента
  (504/502/503) додають поруч `"trace"`.
- **Міграції — нумеровані SQL-файли** в `migrations/` (`001_init.sql`, `002_nutrients.sql`,
  ...), усі застосовуються на старті додатка і мають бути ідемпотентні. **Застосовані міграції
  не редагуються** — кожна зміна схеми йде новим файлом. Alembic на один день не потрібен.
- **Один коміт на блок плану**, а не один коміт на весь день і не один на кожен файл.
- **Перевірки безпеки: «невідомо» ≠ «можна».** Алергени й веганський статус інгредієнта
  беруться зі структурованих даних джерела (таблиця `Allergens`/`Vegan` спеки по колонках,
  теги Open Food Facts), ніколи мовчазне «ок»:
  - **внутрішня спека** без даних (немає джерела, немає таблиці чи колонки, `vegan: None`)
    для `remove_allergen` / `make_vegan` → відмова вибору (один повтор); якщо повтор не
    виправив — явне попередження у `warnings` і `confidence: low`;
  - **Open Food Facts** з порожніми алергенами / `vegan` невідомо → не відмова, а попередження
    «allergen/vegan status not verified: Open Food Facts data incomplete for …» і
    `confidence: low` для цієї заміни; якщо OFF явно містить цільовий алерген чи `vegan: no` —
    відмова, як для спеки;
  - `reduce_sugar` не блокується невідомим статусом — лише попередження.
- **Тестові фікстури з даними корпусу генеруються з корпусу тим самим парсером**, а не
  вписуються руками: ручна фікстура ховає баги парсера.
- Секрети (`GEMINI_API_KEY`, `GROQ_API_KEY`) — тільки через `.env` (в `.gitignore`), в
  `.env.example` — лише назви змінних з коментарями, без реальних значень.

## Схема бази (3 таблиці)

`002_nutrients.sql` додає `documents.nutrients_per_100g JSONB` — таблиця нутрієнтів спеки,
розібрана при інгесті (`{колонка: {kcal, protein_g, fat_g, carbs_g, sugar_g}}`).
`003_allergens.sql` додає `documents.allergens JSONB` — таблиця `Allergens`/`Vegan` на початку
розділу `## Allergens` спеки з тими самими колонками (`{колонка: {allergens: [...], vegan}}`);
NULL = статус невідомий. На старті після міграцій `backfill_allergens` дозаповнює NULL тим
самим парсером з `content` (ембединги не чіпає).

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
  doc_id      TEXT PRIMARY KEY,
  title       TEXT NOT NULL,
  doc_type    TEXT NOT NULL CHECK (doc_type IN ('ingredient_spec','trial_report','guideline')),
  content     TEXT NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE chunks (
  id          BIGSERIAL PRIMARY KEY,
  doc_id      TEXT NOT NULL REFERENCES documents(doc_id) ON DELETE CASCADE,
  chunk_index INT  NOT NULL,
  text        TEXT NOT NULL,
  embedding   VECTOR(384) NOT NULL
);
CREATE INDEX chunks_embedding_idx ON chunks USING hnsw (embedding vector_cosine_ops);

CREATE TABLE reformulation_runs (
  id          BIGSERIAL PRIMARY KEY,
  request     JSONB NOT NULL,
  response    JSONB,
  trace       JSONB NOT NULL DEFAULT '[]',
  status      TEXT NOT NULL,
  duration_ms INT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Повторний інгест того самого `doc_id` замінює старі чанки, не додає дублікати.
`reformulation_runs` логує кожен запуск агента разом із trace — це відповідь на співбесідне
питання "як ти б дебажив агента в продакшені".

## Endpoints (4)

| Метод і шлях | Призначення | Вхід | Вихід |
|---|---|---|---|
| GET /health | Живий сервіс і база | — | `{"status","db","llm_provider"}` |
| POST /documents | Інгест одного документа | `{doc_id, title, doc_type, content}` | `{doc_id, chunks_created}` |
| POST /ask | RAG-відповідь із цитатами | `{question, top_k: 5}` | `{answer, sources: [{doc_id, title, chunk_text, score}]}` |
| POST /reformulate | Агент переформулювання | рецептура + goal + goal_params | substitutions + nutrition + trace |

Чанкування: 200 токенів, перекриття 40, рахуються токенізатором самої `all-MiniLM-L6-v2`
(не словами): модель обрізає вхід на 256 токенах, тож більший чанк ембедер побачив би лише
частково. Текст чанка — зріз оригіналу за offset-ами токенів. `/ask`: якщо відповіді немає в чанках — чесне
"в базі знань немає даних", а не вигадка; запит без жодного заіндексованого документа → 409
`empty_knowledge_base`.

`goal` для `/reformulate` — одне з трьох: `remove_allergen` (параметр `allergen`, один із 14
алергенів ЄС), `reduce_sugar` (параметр `percent` 10–50), `make_vegan` (без параметрів).

## Агент

Звичайний цикл tool calling (не фреймворк): LLM отримує системний промпт, рецептуру, ціль і
опис трьох інструментів, викликає їх, поки не готова відповісти, повертає JSON за схемою.

**Три інструменти:**

| Інструмент | Аргументи | Повертає | Реалізація |
|---|---|---|---|
| `search_knowledge_base` | `query: str, top_k: int = 5` | чанки з doc_id/title/text/score | той самий векторний пошук, що й `/ask` |
| `lookup_product` | `name: str` | нутрієнти/100г, алергени, інгредієнти | Open Food Facts, timeout 5с, in-memory кеш на час запуску |
| `calc_nutrition` | `ingredients: list[{name, grams, nutrients_per_100g}]` | kcal/protein/fat/carbs/sugar на 100г | чиста арифметика на Python, без LLM і мережі |

`calc_nutrition` — інструмент, а не промпт, бо LLM погано рахує зважені середні.

**Обмеження циклу:** максимум 6 ітерацій і 60 секунд. Перевищено → 504 `agent_timeout` +
той trace, що встиг назбирати. Захист від зациклення: якщо модель два рази підряд викликає
той самий інструмент з тими самими аргументами — цикл примусово просить фінальну відповідь.

**Системний промпт, 4 правила:**
1. Спочатку база знань, потім Open Food Facts. Внутрішні спеки пріоритетніші.
2. Кожна заміна посилається на `doc_id` або продукт з Open Food Facts. Без джерела →
   `"confidence": "low"` і запис у `warnings`.
3. Нутрієнти до/після — тільки через `calc_nutrition`, ніколи вручну.
4. Фінальна відповідь — тільки JSON за схемою, без тексту навколо.

Невалідний JSON від LLM → один повтор із текстом помилки, максимум 1 раз. Кожен виклик
інструмента і кожна помилка валідації потрапляють у `trace`.

**Запасний варіант, якщо агент не стабілізується вчасно (орієнтир — 5:00 від старту):**
замість вільного циклу — фіксований пайплайн з трьох кроків, де код сам викликає інструменти
в заданому порядку, а LLM лише формулює пошуковий запит і фінальну відповідь. Якщо
довелось піти цим шляхом — чесно написати про це в README як свідомий компроміс.

**Стан: запасний варіант задіяно.** Вільний цикл на живому Gemini проходив 1–2 з 3 цілей, тож
`/reformulate` працює через `app/agent/pipeline.py`: LLM — план і вибір (2 виклики + до 1
повтору кожен), код — нутрієнти з таблиць спек, `calc_nutrition`, доза цукру, перевірка цілі
й алергенів за даними джерел. Причини і дані — у README («Рішення і компроміси»).

## Дані для RAG

23 markdown-документи у `data/corpus/` (генеруються окремим запитом до Claude, не руками):
15 `ingredient_spec` (функція інгредієнта, дозування, алергени, нутрієнти/100г, чим
замінити; три з них — молоко 2.5%, заморожена полуниця, закваски — додані під демо-йогурт),
6 `trial_report` (звіт з пробної варки), 2 `guideline` (політика з алергенів,
зниження цукру). Інгредієнти мають покривати всі три цілі агента: молоко і рослинні
аналоги, цукор і підсолоджувачі, яйце і замінники, пшеничне борошно і безглютенові суміші.
Кожен документ 200–500 слів, з frontmatter `doc_id, title, doc_type`. Варто переглянути 2–3
документи очима — якщо там немає конкретних чисел і замін, RAG-у нічого буде цитувати.

## Фідбек ПМ (30.09.2026) — план виправлень

Основний блок здано, ПМ знайшов 8 проблем. Робимо **по одному коміту на пункт**, у порядку
нижче (спершу безпека, далі помилки, далі якість, документація в кінці). Кожен пункт
закритий, коли виконано «Готово, коли». Статус: `[ ]` — не почато, `[x]` — зроблено.

### [x] 1+2. Алергени закваски і фікстура, що сховала баг (критично, безпека)

**Проблема.** `allergens.from_spec` читає лише жирний текст у розділі `## Allergens`. У
`spec-yogurt-starter` жирним там лише «certified dairy-free culture», тому спека дає
`allergens: []`, `vegan: None`. Пайплайн відхиляє тільки `vegan is False`, тож `None`
проходить. Результат: йогурт із 10 г bulk-закваски (ферментоване молоко) повертається як
«безмолочний» і «веганський» без попереджень. Тест не ловив, бо `FACTS` у
`tests/test_pipeline.py` вписані руками і закваски там немає. Крім того, `vegan: None` зараз
мають 9 із 15 спек (соєвий напій, цукор, еритрит…) — якщо просто заборонити `None`,
`make_vegan` відкине й соєвий напій.

**Що робимо.**
- Корпус: у кожній `ingredient_spec` розділ `## Allergens` отримує машиночитану таблицю з
  тими самими колонками, що `## Nutrients per 100 g` (рядки `Allergens` і `Vegan`), напр.
  для закваски: bulk → `milk` / `no`, рослинна DVS → `none` / `yes`. Пояснювальний текст
  лишається під таблицею.
- `app/allergens.py`: парсер таблиці → `{колонка: {"allergens": [...], "vegan": bool|None}}`,
  окремо для кожної колонки, як `parse_nutrients_table`.
- Інгест: розбір при інгесті в структуроване поле — нова міграція
  `migrations/003_allergens.sql` (`documents.allergens JSONB`), `retrieval.doc_allergens`
  читає її й повертає факти по колонках; пайплайн бере факти тієї колонки, яку обрав
  `nutrients_column`.
- Пайплайн (`_check_allergens`): невідомий статус інгредієнта «після» (немає джерела,
  немає даних в колонці, `vegan: None`) для `remove_allergen` / `make_vegan` → `ValueError`
  (повтор вибору з текстом помилки); якщо не виправлено — відповідь з явним попередженням.
- Тести: `FACTS` у `tests/test_pipeline.py` генеруються з `data/corpus` через парсер;
  додати регресійний тест ПМ (`test_dairy_starter_blocks_milk_free_claim`, текст у
  фідбеку) і тести парсера на всіх спеках у `tests/test_allergens.py`.

**Готово, коли:** тест ПМ зелений (зараз падає з `DID NOT RAISE`), `from_spec` для bulk-
колонки закваски дає `milk`/`vegan False`, усі 15 спек мають відомий `vegan` у кожній колонці,
`make_vegan` на соєвому напої + рослинній заквасці проходить, повний `pytest` і `ruff` чисті.

### [x] 6. Неправильний ключ → зрозумілий код, а не 502

**Проблема.** `app/llm/base.py::_post_once` віддає будь-яку відповідь `>= 400` як 502
`llm_error`, тож невалідний ключ Gemini (400, `API_KEY_INVALID`) виглядає як збій провайдера.

**Що робимо.** Розпізнати невалідний ключ: Gemini 400 з `API_KEY_INVALID` у тілі, Groq 401
(`invalid_api_key`) → `LLMError(code="llm_invalid_key", status_code=503)` з повідомленням
«GEMINI_API_KEY is invalid», як уже зроблено для `llm_not_configured`. Такий збій не

### [x] 3. Українські питання в `/ask` не знаходять документів

**Що робимо.** Перед пошуком — один виклик `llm.complete` («переклади питання на англійську
для пошуку, поверни лише запит»); якщо питання вже англійською (лише ASCII-літери) — виклик

переінгесту і префіксів `query:`/`passage:`; згадати в README як наступний крок.

**Готово, коли:** recall@5 для українських питань близький до англійських (цифри до/після —
