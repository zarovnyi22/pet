# **Таска: Reformulation Assistant для харчової R&D**

Sep 24, 2026 ·

## **Контекст і мета**

Це навчальна pet-таска під вакансію Backend & AI Engineer у харчовій R&D. За один робочий день з Claude збираєш працюючий сервіс, який покриває весь стек з вакансії: Python, FastAPI, PostgreSQL з pgvector, Docker, LLM, RAG, агент з інструментами. Kubernetes іде бонусом, хмара свідомо пропущена, бо її free tier вимагає банківську картку.

Що таска тренує:

- Проєктування API з Pydantic-схемами і зрозумілими контрактами.

- RAG від початку до кінця: чанкування, ембединги, векторний пошук, відповідь із цитуванням джерел.

- Агент з tool calling: як дати LLM інструменти і не дати їй зациклитися.

- Postgres як основна і векторна база водночас.

- Docker Compose і тести, які не залежать від живого LLM.

Обмеження:

- Тільки безкоштовні сервіси, без банківської картки.

- Орієнтир 8 годин чистої роботи. Все, що не встигається, іде в бонуси.

- Результат запускається однією командою і придатний для демо на співбесіді.

## **Що будуємо**

HTTP-сервіс **Reformulation Assistant**: технолог подає рецептуру продукту і ціль зміни, а сервіс повертає обґрунтовану пропозицію замін інгредієнтів із джерелами і порівнянням нутрієнтів до та після.

User story: «Як технолог R&D, я хочу подати рецептуру йогурту і ціль “прибрати молочний алерген”, щоб отримати список замін, вплив на калорійність і білок, і посилання на внутрішні спеки, на яких ґрунтується рекомендація».

Сервіс складається з трьох частин:

1.  **База знань.** Внутрішні документи R&D лежать у Postgres як чанки з векторами. Це джерело правди для агента.

2.  **RAG-пошук.** Питання в вільній формі про інгредієнти, алергени, функціональні властивості. Відповідь із цитуванням конкретних документів.

3.  **Агент переформулювання.** LLM у циклі викликає інструменти: пошук у базі знань, пошук продукту в Open Food Facts, підрахунок нутрієнтів. Повертає структурований JSON, а не вільний текст.

Приклад запиту до агента:

POST /reformulate

{

"product_name": "Полуничний йогурт 2.5%",

"ingredients": \[

{"name": "молоко 2.5%", "grams": 800},

{"name": "цукор", "grams": 90},

{"name": "полуниця заморожена", "grams": 100},

{"name": "закваска", "grams": 10}

\],

"goal": "remove_allergen",

"goal_params": {"allergen": "milk"}

}

Приклад відповіді:

{

"substitutions": \[

{

"original": "молоко 2.5%",

"replacement": "кокосове молоко 2.5% жиру",

"grams": 800,

"rationale": "Схожа жирність і текстура після ферментації, див. спеку SPEC-014.",

## **Стек і безкоштовні сервіси**

Усе працює без картки. Єдиний зовнішній ключ, який треба отримати, це ключ до LLM.

|----------------------|------------------------------------------------------------|---------------------------------------------------------------|
| Мова і пакети        | Python 3.12, uv                                            | uv ставить залежності за секунди, один файл pyproject.toml    |
| API                  | FastAPI, Pydantic v2, uvicorn                              | Схеми запитів і Swagger UI безкоштовно                        |
| База даних і вектори | PostgreSQL 16 з pgvector, образ pgvector/pgvector:pg16     | Одна база закриває і PostgreSQL, і vector database з вакансії |
| Доступ до бази       | SQLAlchemy 2 async або asyncpg напряму                     | Для одного дня простіше asyncpg з ручним SQL                  |
| Ембединги            | sentence-transformers, модель all-MiniLM-L6-v2, 384 виміри | Локально, без ключа, швидко на CPU                            |
| LLM, основний        | Gemini API через Google AI Studio, модель сімейства Flash  | Free tier без картки, підтримує tool calling і JSON-режим     |
| LLM, запасний        | Groq free tier, моделі Llama                               | Швидкий, також без картки, також tool calling                 |
| LLM, офлайн          | Ollama з qwen2.5:7b                                        | Нуль мережі і лімітів, але потрібно 16 ГБ пам'яті             |
| Дані про продукти    | Open Food Facts API                                        | Без ключа, є нутрієнти і алергени на продукт                  |
| Контейнери           | Docker, Docker Compose                                     | Обов'язково                                                   |
| Kubernetes           | kind або minikube                                          | Локальний кластер, бонус                                      |
| CI                   | GitHub Actions                                             | Безкоштовно для публічного репозиторію, бонус                 |
| Тести                | pytest, pytest-asyncio, httpx                              | Стандарт для FastAPI                                          |

Важливо про LLM: сховати провайдера за одним класом LLMClient з двома методами: complete і complete_with_tools. Провайдер обирається змінною оточення LLM_PROVIDER. Коли впадуть ліміти Gemini, переключення на Groq займає одну змінну, а не годину переписування.

Актуальні ліміти free tier у Gemini і Groq змінюються, тому перед стартом варто зайти на сторінку тарифів і перевірити запити на хвилину і на день. Для одного дня розробки будь-якого з них вистачить, якщо тести не ходять у живий LLM.

## **Функціональні вимоги**

Чотири ендпоінти. Всі тіла запитів і відповідей описані Pydantic-моделями, помилки повертаються в єдиному форматі {"error": {"code": "...", "message": "..."}}.

| **Метод і шлях**  | **Призначення**           | **Вхід**                                   | **Вихід**                                                             |
|-------------------|---------------------------|--------------------------------------------|-----------------------------------------------------------------------|
| GET /health       | Живий сервіс і база       | немає                                      | {"status": "ok", "db": "ok", "llm_provider": "gemini"}                |
| POST /documents   | Інгест одного документа   | {"doc_id", "title", "doc_type", "content"} | {"doc_id", "chunks_created"}                                          |
| POST /ask         | RAG-відповідь із цитатами | {"question", "top_k": 5}                   | {"answer", "sources": \[{"doc_id", "title", "chunk_text", "score"}\]} |
| POST /reformulate | Агент переформулювання    | див. приклад у розділі «Що будуємо»        | див. там само                                                         |

Деталі по кожному:

**POST /documents.** doc_type одне з ingredient_spec, trial_report, guideline. Сервіс ріже текст на чанки по 400 токенів з перекриттям 50, рахує ембединги, зберігає. Повторний інгест того самого doc_id замінює старі чанки, а не додає дублікати. Окремо є CLI-команда python -m app.ingest data/corpus/, яка заливає всю папку за раз.

**POST /ask.** Питання ембедиться тією самою моделлю, шукаються top_k найближчих чанків за косинусною відстанню, LLM отримує їх у контексті з інструкцією відповідати тільки з них. Якщо в чанках немає відповіді, поле answer містить чесне «в базі знань немає даних», а не вигадку. Запит без жодного заіндексованого документа повертає 409 з кодом empty_knowledge_base.

**POST /reformulate.** goal одне з трьох значень:

- remove_allergen, параметр allergen з переліку 14 алергенів ЄС.

- reduce_sugar, параметр percent від 10 до 50.

- make_vegan, без параметрів.

Агент працює не більше 6 ітерацій і не більше 60 секунд. Перевищив ліміт, повертає 504 з кодом agent_timeout і тим trace, що встиг назбирати. Поле trace у відповіді обов'язкове: це список викликаних інструментів з аргументами, без нього агент неможливо дебажити і показати на співбесіді.

Кожна заміна в substitutions має непорожній sources. Заміна без джерела в базі знань чи в Open Food Facts позначається "confidence": "low" і потрапляє в warnings.

## **Дані**

Корпус для RAG генерується Claude за 15 хвилин, справжні PDF шукати не треба. Замовляєш 20 markdown-документів у папку data/corpus/, кожен на 200 до 500 слів, з frontmatter doc_id, title, doc_type.

| **Тип**         | **Кількість** | **Що всередині**                                                                                                            |
|-----------------|---------------|-----------------------------------------------------------------------------------------------------------------------------|
| ingredient_spec | 12            | Спека інгредієнта: функція в продукті, дозування, алергени, нутрієнти на 100 г, чим можна замінити і з якими застереженнями |
| trial_report    | 6             | Звіт з пробної варки: що замінили, як змінилася текстура і смак, оцінка сенсорної панелі, висновок                          |
| guideline       | 2             | Внутрішня політика з алергенів і правила зниження цукру без втрати об'єму                                                   |

Інгредієнти для спек підбирай так, щоб вони покривали всі три цілі агента: молоко і його рослинні аналоги, цукор і підсолоджувачі, яйце і замінники, пшеничне борошно і безглютенові суміші. Тоді демо на будь-яку ціль знайде що цитувати.

Схема бази, три таблиці:

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (

doc_id TEXT PRIMARY KEY,

title TEXT NOT NULL,

doc_type TEXT NOT NULL CHECK (doc_type IN ('ingredient_spec','trial_report','guideline')),

content TEXT NOT NULL,

created_at TIMESTAMPTZ NOT NULL DEFAULT now()

);

CREATE TABLE chunks (

id BIGSERIAL PRIMARY KEY,

doc_id TEXT NOT NULL REFERENCES documents(doc_id) ON DELETE CASCADE,

chunk_index INT NOT NULL,

text TEXT NOT NULL,

embedding VECTOR(384) NOT NULL

);

CREATE INDEX chunks_embedding_idx ON chunks USING hnsw (embedding vector_cosine_ops);

CREATE TABLE reformulation_runs (

id BIGSERIAL PRIMARY KEY,

request JSONB NOT NULL,

response JSONB,

trace JSONB NOT NULL DEFAULT '\[\]',

status TEXT NOT NULL,

duration_ms INT,

created_at TIMESTAMPTZ NOT NULL DEFAULT now()

);

Таблиця reformulation_runs потрібна, щоб кожен запуск агента був залогований разом із trace. На співбесіді це відповідь на питання «як ти б дебажив агента в продакшені».

Міграції: один SQL-файл migrations/001_init.sql, який застосовується на старті додатка. Alembic на один день не потрібен.

## **Агент**

Агент це звичайний цикл tool calling без фреймворків: LLM отримує системний промпт, рецептуру, ціль і опис трьох інструментів, викликає їх, поки не готова відповісти, і повертає JSON за схемою. LangChain чи LangGraph брати не треба, власний цикл на 50 рядків прозоріший і краще виглядає на співбесіді.

flowchart TD

A\[Запит reformulate\] --\> B\[Зібрати промпт:\<br/\>рецептура + ціль + інструменти\]

B --\> C\[Виклик LLM\]

C --\> D{Відповідь містить\<br/\>tool call?}

D -- так --\> E\[Виконати інструмент,\<br/\>додати в trace\]

E --\> F{Ітерацій \< 6\<br/\>і час \< 60 с?}

F -- так --\> C

F -- ні --\> G\[504 agent_timeout + trace\]

D -- ні --\> H\[Валідація JSON\<br/\>через Pydantic\]

H -- помилка --\> I\[Повтор з текстом помилки,\<br/\>максимум 1 раз\]

I --\> C

H -- ok --\> J\[Запис у reformulation_runs,\<br/\>відповідь 200\]

Кожен виклик інструмента і кожна помилка валідації потрапляють у trace, тому після будь-якого запуску видно, що саме робила модель.

Інструменти, рівно три:

| **Інструмент**        | **Аргументи**                                        | **Що повертає**                                                               | **Реалізація**                                                                                      |
|-----------------------|------------------------------------------------------|-------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------|
| search_knowledge_base | query: str, top_k: int = 5                           | Список чанків з doc_id, title, text, score                                    | Той самий векторний пошук, що й у /ask                                                              |
| lookup_product        | name: str                                            | Нутрієнти на 100 г, алергени, список інгредієнтів першого знайденого продукту | HTTP-запит до Open Food Facts search API, таймаут 5 с, результат кешується в пам'яті на час запуску |
| calc_nutrition        | ingredients: list of name, grams, nutrients_per_100g | kcal, protein_g, fat_g, carbs_g, sugar_g на 100 г готового продукту           | Чиста арифметика на Python, без LLM і мережі                                                        |

Чому calc_nutrition це інструмент, а не промпт: LLM погано рахує зважені середні. Це гарний приклад для співбесіди про те, що віддавати моделі, а що коду.

Системний промпт має містити чотири правила:

1.  Спочатку шукати в базі знань, потім у Open Food Facts. Внутрішні спеки пріоритетніші.

2.  Кожна заміна посилається на doc_id або на продукт з Open Food Facts. Без джерела ставити confidence low.

3.  Нутрієнти до і після рахувати тільки через calc_nutrition, ніколи вручну.

4.  Фінальна відповідь тільки в JSON за схемою, без тексту навколо.

Захист від зациклення: якщо модель два рази підряд викликає той самий інструмент з тими самими аргументами, цикл примусово просить фінальну відповідь.

**Docker.** Dockerfile двостадійний: на першій стадії uv ставить залежності, на другій лише код і venv. Модель ембедингів завантажується на етапі збірки образу, а не при старті, інакше кожен контейнер тягне 90 МБ з інтернету. У docker-compose два сервіси: api і db, у db volume для даних і healthcheck через pg_isready, api стартує після здорової бази.

**Конфігурація.** Все через змінні оточення і pydantic-settings: DATABASE_URL, LLM_PROVIDER, GEMINI_API_KEY, GROQ_API_KEY, EMBEDDING_MODEL, AGENT_MAX_ITERATIONS, AGENT_TIMEOUT_SECONDS. Файл .env.example з усіма змінними і коментарями, справжній .env в .gitignore.

**Тести.** Мінімальний набір, який проходить без ключів і без інтернету:

| **Тест**               | **Що перевіряє**                                                                                      | **Залежності**            |
|------------------------|-------------------------------------------------------------------------------------------------------|---------------------------|
| test_chunking.py       | Розмір чанків, перекриття, порожній текст                                                             | жодних                    |
| test_calc_nutrition.py | Зважене середнє на 100 г, нульова маса, відсутні нутрієнти                                            | жодних                    |
| test_agent_loop.py     | Цикл з FakeLLM: викликає інструмент, зупиняється на ліміті, повторює при невалідному JSON, пише trace | FakeLLM                   |
| test_api.py            | /health, /documents, /ask через httpx.AsyncClient з FakeLLM і фейковим ембедером                      | Postgres з docker compose |

Інтеграційний тест бере базу з DATABASE_URL і пропускається через pytest.mark.skipif, якщо змінної немає. Живий LLM у тестах не викликається ніколи.

**README.** Шість блоків: що це і для кого, архітектурна схема в mermaid, як запустити за 3 команди, приклади curl на кожен ендпоінт, як працює агент з прикладом trace, що б зробив далі з більшим часом. Останній блок на співбесіді читають найуважніше.

**Логи.** Структурні JSON-логи через стандартний logging з одним форматтером. Кожен запит отримує request_id, який прокидається в логи агента.

## **Бонусні завдання**

Бонуси брати тільки після того, як основна частина пройшла чекліст готовності. Кожен з них закриває окремий пункт з вакансії, тому порядок за цінністю для співбесіди.

**1. Kubernetes на kind, приблизно 1 година.** Папка k8s/ з п'ятьма маніфестами: Namespace, Secret з ключами і DATABASE_URL, Deployment і Service для api з liveness і readiness на /health, StatefulSet і Service для Postgres з PersistentVolumeClaim. Перевірка: kind create cluster, kind load docker-image, kubectl apply -k k8s/, kubectl port-forward і curl на /health. У README додати ці команди. Helm не потрібен.

**2. GitHub Actions, приблизно 30 хвилин.** Один workflow на push: підняти Postgres як service container з образом pgvector, встановити залежності через uv, прогнати ruff і pytest, зібрати Docker-образ без push. Бедж зі статусом у README.

**3. Гібридний пошук, приблизно 45 хвилин.** До векторного пошуку додати повнотекстовий через tsvector у Postgres і злити результати через Reciprocal Rank Fusion. Назви інгредієнтів і коди спек на кшталт SPEC-014 векторний пошук знаходить погано, це гарна тема для розмови про обмеження RAG.

**4. Оцінка якості RAG, приблизно 45 хвилин.** Файл eval/questions.jsonl з 10 парами питання і очікуваний doc_id, скрипт, який рахує recall@5 для пошуку. Це показує, що людина вміє міряти, а не лише будувати.

**5. Хмара, тільки якщо вже є акаунт.** Найпростіший шлях GCP Cloud Run для api і Neon або Supabase для Postgres з pgvector, у обох є free tier. ## **Критерії готовності**

Таска закрита, коли відмічено всі пункти основного блоку. Бонуси не впливають на готовність.

**Запуск**

- git clone і docker compose up --build на чистій машині піднімають сервіс без ручних кроків, крім копіювання .env.example в .env і вставки ключа LLM.

- GET /health повертає статус бази і назву провайдера LLM.

- Swagger UI на /docs показує всі чотири ендпоінти з прикладами тіл.

**Дані і RAG**

- Команда ingest заливає всі 20 документів, повторний запуск не створює дублікатів.

- POST /ask повертає відповідь і список джерел з doc_id і score.

- На питання поза корпусом, наприклад про погоду, сервіс відповідає, що даних немає, а не вигадує.

- Індекс hnsw створено, пошук йде через оператор косинусної відстані.

**Агент**

- POST /reformulate працює для всіх трьох цілей на прикладі йогурту з розділу «Що будуємо».

- Відповідь проходить Pydantic-валідацію, кожна заміна має sources або позначку confidence low.

- Нутрієнти до і після пораховані інструментом calc_nutrition, це видно в trace.

- Ліміт ітерацій і таймаут спрацьовують, перевірено тестом з FakeLLM.

- Кожен запуск збережено в reformulation_runs разом із trace і тривалістю.

**Якість коду**

- pytest проходить без ключів LLM і без інтернету.

- ruff check і ruff format --check чисті.

- Провайдер LLM переключається однією змінною оточення, перевірено вручну на Gemini і Groq.

- Секрети не закомічені, є .env.example.

**Документація**

- README містить схему архітектури, команди запуску, curl на кожен ендпоінт і приклад trace.

- Є розділ «що б зробив далі» з 3 до 5 пунктами.

- Історія комітів читабельна: один коміт на блок плану, а не один на весь день.
