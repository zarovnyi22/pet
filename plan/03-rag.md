# Блок 3 — RAG (орієнтир: 1.5 години)

## Промпт для Claude Code

```
Прочитай CLAUDE.md. Реалізуй тільки блок RAG:
1. app/retrieval.py — векторний пошук у pgvector: ембедиш питання тією самою моделлю,
   шукаєш top_k найближчих чанків за косинусною відстанню (оператор hnsw-індексу).
2. app/llm/base.py — інтерфейс LLMClient з методами complete і complete_with_tools.
3. app/llm/gemini.py — реалізація через Gemini API, провайдер обирається змінною оточення
   LLM_PROVIDER.
4. POST /ask — {question, top_k: 5} -> {answer, sources}. LLM отримує знайдені чанки в
   контексті з інструкцією відповідати тільки з них. Якщо в чанках немає відповіді — answer
   містить чесне "в базі знань немає даних", а не вигадку. Запит, коли в базі взагалі нема
   жодного документа, повертає 409 з кодом empty_knowledge_base.

Постав свій справжній GEMINI_API_KEY у .env перед тестуванням (я вже це зробив/зроблю сам).

Коли скажу, що контрольна точка пройдена — закоммить усе з повідомленням "Block 3: RAG and
LLM client" і запуш у `origin main`. Переконайся, що .env з реальним ключем не потрапляє в
коміт (тільки .env.example).
```

## Перевір, перш ніж йти далі

Запит на тему, яка є в корпусі:
```
curl -X POST http://localhost:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "чим замінити яйце в бісквіті", "top_k": 5}'
```
Очікується відповідь, яка реально посилається на конкретний `doc_id` з `data/corpus/`.

Запит на щось поза темою корпусу (наприклад про погоду) — має чесно сказати, що даних
немає, а не вигадати відповідь.

Запит без жодного заіндексованого документа (якщо перевіряєш на чистій базі) — 409
`empty_knowledge_base`.
